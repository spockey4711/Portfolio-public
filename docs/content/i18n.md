# Internationalization (i18n)

**Purpose:** how the site serves German and English from one component tree — the routing
shape, the copy contract, the SEO cross-linking, and the exact steps to translate the next
route. The *why* behind the model is
[ADR-0006](../../private-docs/docs/architecture/decisions/0006-i18n-and-localization.md); this doc is the working
reference.

Related: [ADR-0006](../../private-docs/docs/architecture/decisions/0006-i18n-and-localization.md) ·
[SEO and metadata](seo.md) · [content & voice](content-and-voice.md)

## The model in one paragraph

German is canonical and lives at the bare root (`/`, `/projekte`, `/blog`). English lives
under an `/en` prefix with translated path segments (`/en`, `/en/projects`, `/en/blog`).
There is no locale in the German URL and no request-time middleware — locale is decided
entirely by which route-group folder a page lives in. The same component tree renders both
languages; only the strings and the enclosing `<html lang>` differ.

## Where things live

| Concern | File | Notes |
|---|---|---|
| Locale model | `lib/i18n/locale.ts` | `Locale`, `locales`, `defaultLocale`, `localeTag`, `openGraphLocale`, `isLocale`. Dependency-free. |
| Route map | `lib/i18n/routes.ts` | Every path, both locales; `localizedPath`, `alternatesFor`, `counterpartPath`, `isRouteTranslated`, `translatedRoutes`. |
| Copy | `content/copy/` | `de.ts` (canonical shape), `en.ts` (checked against it), `getCopy(locale)`. |
| German tree | `app/(de)/` | Canonical, unprefixed. Route group `(de)` adds no URL segment. |
| English tree | `app/(en)/en/` | The `/en` prefix. |
| Root layouts | `app/(de)/layout.tsx`, `app/(en)/layout.tsx` | One per locale; own the `<html lang>` shell and root metadata. |
| Shared chrome | `components/chrome/SiteChrome.tsx` | Nav, footer, command palette, boot scripts — locale-parameterized, rendered by both layouts. |
| Shared onepager | `components/sections/Onepager.tsx` | The sections, rendered by both `/` and `/en`. |
| Root metadata | `lib/seo/metadata.ts` | `buildRootMetadata(locale)` — title, OG, canonical, hreflang. |
| Language toggle | `components/chrome/Nav.tsx` (`LanguageToggle`) | Uses `counterpartPath`. |
| Sitemap | `app/sitemap.ts` | Lists each translated route's live locale variants with absolute hreflang. |

## Two root layouts, one tree

The App Router route group `app/(de)/` is a URL-invisible folder, so its pages stay at the
bare root while `app/(en)/en/` gets the `/en` prefix. Each group has its own root layout that
owns exactly two locale-specific things:

- the `<html lang>` shell — `lang={localeTag[locale]}` (`de-DE` / `en`);
- the root metadata — `buildRootMetadata(locale)`.

Everything below `<body>` is the shared `<SiteChrome locale>`, so the nav, footer, boot
scripts and page content exist once and render per locale. Because there are two roots and no
single shared root layout, the global `app/not-found.tsx` renders its own `<html>`/`<body>`.

## The copy contract

Components never import a language singleton. They read strings through `getCopy(locale)`,
which returns the typed `Copy` object for that locale:

```ts
import { getCopy } from "@/content/copy";
const { nav } = getCopy(locale);
```

`content/copy/de.ts` defines the canonical `Copy` type; `content/copy/en.ts`
`satisfies Copy`, so **a missing or misshaped English string is a compile error, not a runtime
blank.** Add a new string to `de.ts` first (that extends the type), then fill the English
value in `en.ts` — typecheck tells you if you forgot.

> **Deprecated shim.** `content/copy/index.ts` still exports `copy = deCopy` for consumers not
> yet migrated to `getCopy(locale)` (the blog post cards — `PostCard`/`PostMeta` — still read
> it; the blog index pages no longer do). It is `@deprecated`; do not add new usages, and
> delete it once every consumer reads copy per-locale. The legal pages read their own
> per-locale module (`content/legal.ts`, `getImprint`/`getPrivacy`), not this shim.

## The route map is the single source of truth

All paths come from `lib/i18n/routes.ts` — never hard-code `/en/...` in a component. Key
helpers:

- `localizedPath(key, locale[, slug])` — the path for a route in a locale.
- `localizedAnchor(hash, locale)` — a home-anchor href (`/#projekte` vs `/en#projekte`).
- `alternatesFor(key, locale[, slug])` — `{ canonical, languages }` for `generateMetadata`;
  German is `x-default`.
- `counterpartPath(pathname, from)` — the other locale's URL for the language toggle.
- `isRouteTranslated(route, locale)` / `translatedRoutes` — the publish gate (below).

## The `translatedRoutes` gate — how to translate a route

Translation lands **one route at a time**. `translatedRoutes` in `lib/i18n/routes.ts` is the
allow-list of route keys whose English variant is actually live; until a key is in it, the
English variant is never advertised. This is what stops half-finished English pages from
leaking: the language toggle falls back to the English home, cross-page link lists hide the
untranslated link, and the sitemap omits the variant.

Today the set is `{ "home", "projectsIndex", "projectDetail", "uses", "now", "imprint",
"privacy", "blogIndex" }` (the onepager, the projects index at `/en/projects`, the per-project
detail pages at `/en/projects/<slug>`, the uses inventory at `/en/uses`, the now snapshot at
`/en/now`, the legal pages at `/en/imprint` + `/en/privacy`, and the blog index at `/en/blog`,
S5-1a-f). The legal pages are the one exception to the sitemap rule: they are noindex (like
their German twins), so they gain reciprocal hreflang but stay out of the sitemap.

`blogPost` deliberately stays **out** of `translatedRoutes` even now that EN posts exist
(S5-1g): blog posts are translated opt-in **per post** (a real, ongoing content effort), so a
coarse per-key gate is the wrong tool. The per-post switch is `translatedBlogPostSlugs` in
`lib/i18n/routes.ts` — a client-safe set of the slugs whose English translation is published.
Translating a post means two edits: add the slug to that set, and add the parallel MDX file at
`content/blog/en/<slug>.mdx`. The blog registry (`getEnglishPosts` in `lib/content/blog.ts`)
cross-checks the two at build time and fails loudly on any drift, so an advertised translation
can never lack its file and a stray file can never ship unadvertised. Everything reads that one
set: `getPostsForLocale("en")` lists only translated posts on `/en/blog`; the `/en/blog/<slug>`
route pre-renders only those slugs (`dynamicParams=false`, so an untranslated slug is a static
404 that is never linked); the DE and EN post metadata pair reciprocal hreflang only for
translated posts; the sitemap adds the English twin only for translated posts; and the language
toggle deep-links a translated post to its twin but sends an untranslated one to `/en/blog`
(never a 404, never German under `/en`). To ship the next translated route (a whole new page
type, not another post):

1. Add the English page under `app/(en)/en/` (e.g. `app/(en)/en/blog/page.tsx`), rendering
   the shared components with `locale="en"`.
2. Add the English copy (in `content/copy/en.ts`, or a parallel locale list like
   `content/now.ts`) for every string that page needs.
3. Give the route its `alternatesFor(...)` in the page's `generateMetadata`.
4. **Widen the gate:** add the route key to `translatedRoutes`.
5. The toggle, the cross-page links and the sitemap now include it automatically — no other
   wiring. Add/adjust the unit tests in `tests/unit/` and update this table's mention if the
   live set changed.

The path segments themselves already live in `routes.ts` (`staticPaths` / `dynamicPaths`); a
new route needs an entry there too if it is not already listed.

## SEO cross-linking

Root and per-page metadata emit `canonical` plus `de-DE` / `en` / `x-default` hreflang
alternates from `alternatesFor(...)`, and the sitemap (`app/sitemap.ts`) lists each translated
route's live locale variants with absolute hreflang URLs. Because both read the same route
map and the same `translatedRoutes` gate, the alternates and the sitemap can never point at an
English URL that does not exist. German is always the `x-default` and is never ranked below
its English twin. See [seo.md](seo.md) for the full metadata contract.

## EN completeness audit (S5-1h)

The wrap-up pass after the route tasks (S5-1a-g) landed. It confirms every live English route
is complete on all six axes below, and the checks are pinned by `tests/e2e/i18n.spec.ts` so a
regression fails CI rather than silently shipping. German stays canonical and `x-default`
everywhere; the legal pages are noindex (reciprocal hreflang, no sitemap entry).

| EN route | `<html lang="en">` | canonical | de-DE/en/x-default | in sitemap | toggle round-trips | no untranslated leakage |
|---|---|---|---|---|---|---|
| `/en` | ok | ok | ok | ok | ok | ok |
| `/en/projects` | ok | ok | ok | ok | ok | ok |
| `/en/projects/<slug>` | ok | ok | ok | ok | ok | ok |
| `/en/uses` | ok | ok | ok | ok | ok | ok |
| `/en/now` | ok | ok | ok | ok | ok | ok |
| `/en/imprint` | ok | ok | ok | noindex | ok | ok |
| `/en/privacy` | ok | ok | ok | noindex | ok | ok |
| `/en/blog` | ok | ok | ok | ok | ok | ok |
| `/en/blog/<slug>` (translated) | ok | ok | ok | ok | ok | ok |

Notes from the audit:

- **No untranslated leakage.** All shared chrome reads `getCopy(locale)` — nav, footer,
  terminal, blog empty state, metadata, and (closed in S5-1h) the **command palette**, which
  previously rendered German on every `/en` route because it read the deprecated `copy`
  singleton. The palette now takes a `locale` prop from `SiteChrome` and builds its copy,
  command registry and terminal context per locale, so its ⌘K entries and their navigation
  targets are English under `/en`.
- **Toggle.** `counterpartPath` deep-links each route to its twin, falls back to `/en` for an
  untranslated route (e.g. `/primitives`), and sends an untranslated blog post to `/en/blog` —
  never a 404, never German under `/en`.
- **Deliberate German fallback.** The global 404 (`app/not-found.tsx`) renders in German: with
  two locale roots there is no shared layout to know the locale, so it uses `defaultLocale`.
  This is by design, not leakage.
- **Tracked parity gap (outside these axes).** `/en/projects/<slug>` still lacks the branded
  OG/Twitter card and the `projectJsonLd`/`BreadcrumbList` structured data its German twin
  carries (S2-1/S5-2/S5-3 shipped German-only for the detail route). This is not lang, canonical,
  hreflang, sitemap, toggle or leakage, so it is out of S5-1h's scope; it is logged as backlog
  **S5-5** rather than folded in here.

## Adding a whole new locale

Out of scope today (YAGNI — see ADR-0006's rejected alternatives), but the shape is ready:
extend `Locale`/`locales`/`localeTag`, add the copy file, add the route group and its paths.
Revisit a message-catalog framework only if locale count or string volume grows.
